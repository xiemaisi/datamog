# Datamog — Project Instructions

Educational Datalog implementation with multiple evaluation backends — SQL (Postgres, SQLite via bun:sqlite, sql.js/WASM) and pure-TS in-memory interpreters (naive, seminaive). Every backend honours the same language semantics; the SQL ones go via a translator, the interpreters evaluate the AST directly. TypeScript/Bun monorepo. Uses **bun** as package manager and runtime — do not use pnpm/npm/yarn.

Before running anything, verify `bun` is on PATH (`which bun`). If it is not, install via `curl -fsSL https://bun.sh/install | bash` and add `$HOME/.bun/bin` to PATH for the session (`export PATH="$HOME/.bun/bin:$PATH"`). The installer does not persist PATH, so export it on every new shell.

Bun ≥ 1.3.0 is required (root `engines` field).

The Postgres tests skip themselves when `DATABASE_URL` is unset, which is how they
once went stale for a whole branch. **`bun run test:pg`** is the one command that runs
them: it creates a throwaway cluster, runs the whole suite against it, and deletes it
again (`scripts/test-postgres.sh`). It runs strictly more than a bare `bun test`, which
skips every Postgres-gated suite. Pass `PGTESTPORT=55444` if 55432 is taken, and
`-- <paths>` to narrow the run.

CI does the same with a `postgres:16` service container
(`.github/workflows/postgres.yml`). Both set `DATAMOG_REQUIRE_POSTGRES=1`, which makes
`require-postgres.test.ts` fail if `DATABASE_URL` is missing or the server does not
answer — otherwise a broken container turns every Postgres-gated suite into no tests at
all and still reports green, which is the original staleness failure. Do **not** key
that on `CI`: ci.yml's Quality Gate legitimately runs `bun test` with no database.

By hand, when you want the cluster to outlive one run:

```bash
initdb -D /tmp/pgtest/data -U postgres --auth=trust
pg_ctl -D /tmp/pgtest/data -l /tmp/pgtest/server.log -o "-p 55432 -k /tmp/pgtest" start
createdb -h 127.0.0.1 -p 55432 -U postgres datamog_test
DATABASE_URL=postgres://postgres@127.0.0.1:55432/datamog_test bun test
pg_ctl -D /tmp/pgtest/data stop                                          # when done
```

Postgres keeps tables and views between runs, so a sequence of hand-run programs
against one database needs `psql ... -c 'DROP SCHEMA public CASCADE; CREATE SCHEMA
public;'` between them. The examples suite already does that per example, and
`test:pg` sidesteps it by building the cluster fresh.

**`pg-mem` is not a substitute**, checked rather than assumed: of 17 SQL shapes this
dialect emits, 4 behave as real Postgres does. `WITH RECURSIVE` is unimplemented (so
no recursive predicate at all), `IS NOT DISTINCT FROM` does not parse, and
`jsonb_typeof` / `#>>` / `generate_series` / `string_agg` / bitwise `#` are missing.
Worse, the two shapes real Postgres *rejects* — `to_jsonb('x')` on an `unknown`
literal and a bare `GROUP BY NULL` — it rejects for unrelated reasons, so it cannot
tell those bugs from their fixes.

## Architecture

Monorepo with Bun workspaces. Dependency graph (arrows point from a
package to its dependencies, i.e. from consumer to foundation):

```
cli  ──────────────► imports everything (also drives the interactive REPL)
  │
  ├─► repl     (incremental REPL session engine — declarations/rules/queries accumulate)
  │
  ├─► loader/{csv,jsonl,json,gsheet,mermaid}  (json package also exports UrlJsonLoader for HTTP/HTTPS sources)
  │       │
  │       └─► engine (SQL translator, executor, Backend/SqlDialect interfaces)
  │              │
  │              ├─► backend/{postgres,sqlite,sqljs}  (implement SqlDialect)
  │              ├─► backend/native     (no SQL; naive evaluator)
  │              ├─► backend/seminaive  (no SQL; seminaive evaluator, reuses native's planner)
  │              │
  │              └─► core (analyzer, type inference)
  │                     │
  │                     └─► parser (Langium grammar, generated AST, post-processing)
  │
  └─► backend/*, engine, core, parser, repl (all directly)

playground (Preact + Vite SPA, uses parser/core/engine/backend-sqljs via sql.js in a Web Worker; smart auto-complete wired in)
vscode-extension (Langium LSP — syntax highlighting, validation, smart auto-complete)
```

A sibling Python package lives outside the Bun workspace at `python/datamog-magic/` — an IPython cell magic (`%%datamog`) that drives the CLI in `--repl --json` mode over stdin/stdout, with optional `--df NAME` to bind query results to a pandas DataFrame.

### Key modules

- `packages/parser/src/datamog.langium` — Langium grammar defining the Datalog syntax; lexer/parser/AST types are generated from this. Note it has **no cross-references**: every name (`predicate=Identifier`, `Actual.param`, …) is a plain string, since a Datalog name means whatever its position says. That is why the editor's completion and definition providers are hand-written rather than Langium defaults
- `packages/parser/src/index.ts` — four parse entry points, one per (raw vs post-processed) × (throwing vs best-effort) combination: `parse` (post-processed, throws), `parseRaw` (grammar shape, throws — what the elaborator uses), `parseLenient` (post-processed, best-effort), `parseRawLenient` (grammar shape, best-effort — what editor features keyed on source shapes use, since post-processing lowers away `Ctor(...)` and `_`). All four run `liftHeadAnnotations` + `defaultColumnTypes`. Also exports `propertySpan(node, property)`, the single place coupling to Langium's CST helpers so `datamog-core` can locate an identifier's source span while staying Langium-free
- `packages/parser/src/post-process.ts` — post-parse transforms: don't-care variable (`_`) desugaring, numeric literal `rawText` preservation, aggregate `FunctionCall → AggregateCall` rewrite in rule heads, `BracketAccess` splitting into `Subscript` or `Slice` based on whether a `:` was present (the grammar parses a single `BracketAccess` to avoid an LL(k) ambiguity), and the whole **proof-term / ADT desugar** (proof-column injection, constructor-term matching, capture shorthand) which lowers onto the existing `value` machinery, plus `synthesiseContractChecks` (first in `postProcess`, so a synthesised contract check is then treated as an ordinary `!-`). The grammar shares one slot three ways (`Expression ('as' name (': ' type)? | ':' (type | refinement))?`), so `liftHeadAnnotations` handles all three: run in `parseRaw` (not `postProcess`) so no later stage sees an `AnnotatedHeadTerm`, it records **head type annotations** (`h(x: integer)`) on `head.argTypes` (undefined per unannotated position; array absent when the rule has none), then calls `extractRefinements` (`refinements.ts`) and `substituteHeadNames` (`head-names.ts`). Also in `parseRaw`, `defaultColumnTypes` fills the type of any **unannotated input-predicate column** with `string` (the grammar makes the `: type` optional), so downstream sees a concrete `ColumnDecl.type` (a few readers still fall back to `?? "string"` since the generated type stays optional).
- `packages/core/src/ast.ts` — re-exports Langium-generated AST types as the canonical AST; widens `HeadAtom`/`Rule.head.args` to include the synthesised `AggregateCall` nodes and `Expression` to include the post-processed `Subscript`/`Slice`; adds the optional `HeadAtom.argTypes` (head annotations), `isFloatLiteral`, and `asCoreRule` (asserts a parsed+post-processed parser `Rule` as a core `Rule` at the boundary, since parsing strips `AnnotatedHeadTerm` and post-processing injects `AggregateCall`)
- `packages/core/src/analyzer.ts` — EDB/IDB classification, arity tracking, safety checking (fixed-point iteration — order-independent), dependency graph, Tarjan's SCC, recursion detection, non-linear recursion detection, type-compatibility checks for comparisons/equalities
- `packages/core/src/types.ts` — type inference (fixed-point iteration). Column types must be exactly one of `string`/`integer`/`float`/`boolean`/`value`/`null`, each optionally nullable (`T?`, a separate bit rather than a member). `value` is the union of every JSON shape: primitive leaves, arrays, objects, and a JSON `null` inside one; stored as JSONB on Postgres, canonical TEXT on SQLite/sql.js. `null` is the type of the literal, a sibling of the primitives rather than a subtype, so `string ⊓ integer` is still ⊥. The type order is a lattice with `value` as top. A variable shared across atoms **within** a rule takes the `meetTypes` greatest lower bound (incompatible primitives like `string`/`integer` error, since one value must fit every position); a column combined **across** sibling rules takes the `unifyColumnType` total least-upper-bound join (incompatible primitives widen to `value`, never error). `joinTypes` (strict, `integer`↔`float` only) backs arithmetic / range bounds; `joinTypesWithJsonLift` (adds primitive↔`value`) backs compatibility checks (atom arg vs column type, comparison ops). The translator's `liftToJsonIfNeeded` emits the runtime `dialect.toJson` lift these promise. Per-rule validation of range-bound types, operator operand types, function-argument types, comparison compatibility, and rejection of negative integer literals in subscript/slice positions. `columnTypesCompatible(inferred, declared)` is the directional subtype check (`joinTypesWithJsonLift(inferred, declared) === declared`, i.e. declared must equal or widen inferred, never narrow it; a `value` cannot satisfy a declared `integer`). **Head annotations** (`head.argTypes`) are per-rule and per-argument (a rule annotates any subset; sibling rules may differ or omit), checked by `checkHeadAnnotations` against each rule's own contribution, never used to drive inference. They propagate as **assume-guarantee contracts**: `publishedTypes` (= `columnTypes` widened by annotations) is what consumers and module boundaries (`checkModuleBoundaries`) are checked against, while a predicate's own body sees its inferred `columnTypes` (so a `value`-declared recursive predicate can still do arithmetic on itself). Codegen uses `columnTypes` only — annotations never change emitted SQL. See `doc/design/type-lattice.md`
- `packages/core/src/nullness.ts` — nullness inference, a second component beside the base type rather than an element in its lattice (adding `null` below the primitives would make `string ⊓ integer` inhabited). `columnNullness` per predicate is a least fixed point seeded **non-null** and rising, so a recursive predicate is non-null when its base case is; EDB columns take their declared `?`. `nonNullVars` per body is the per-rule refinement, a fixed point over the conjuncts (a body has no control flow, so a guard written last refines an atom written first): `X <> null`, `not (X = null)`, any ordering (all four are strict at a null, so one that holds has non-null operands), a range atom, and `X = e` for non-null `e`, each proving every variable in a **strict position** of the operand. `refineTrue` may flip through a `!` into `refineFalse`, `!e` being true only where `e` has a value and is false; the reverse flip is unsound and `refineFalse` does not do it, since `!e` failing also covers `e` having no value. `Overload` in `builtins.ts` carries a required `nulls: NullBehaviour` holding two bits: `strict` (null in → null out, licensing the backwards reasoning refinement does) and `total` (never invents a NULL, licensing the forwards reasoning column inference does). They are independent — `/` is strict but partial, `=` is total but not strict — and `nulls` is a required parameter, so a new builtin that omits it does not compile; an unresolvable case defaults to nullable, so the analysis only ever fails to notice non-nullness. `publishedNullness` (= `columnNullness` widened by `?` annotations) is the contract for consumers and module boundaries; codegen reads `columnNullness`. `packages/core/src/nullness-diagnostics.ts` holds the warnings: nullable filter, complementary-ordering gap, `not` over an ordering keeping the null row, `<>` over a partial operand (`partial-inequality`), `defined(X)` on a bare variable (`constant-defined`), and the opt-in undefined-expression warning behind `--warn-undefined`. `packages/core/src/partiality.ts` answers the other question, "can this expression have no value", syntactically and without a rule context. See `doc/design/null-as-a-value.md`; `nullness-tracking.md` is partly superseded
- `packages/core/src/definitions.ts` — cursor-driven go-to-definition: `findDefinition(program, offset)` answers "what name is at this offset and where is it defined", covering predicates, variables (binding occurrences within the enclosing rule, including constructor patterns, which destructure and so bind), proof-term constructors, and `:=` bindings. Complements `references.ts`, which answers the pull-shaped version ("every clickable predicate span") that the playground needs to underline spans; both share `findPredicateDefinitions`. Runs on a **raw, un-post-processed** program (`parseRawLenient`) because post-processing lowers away `Ctor(...)` and `_`, and because navigation must survive a file that doesn't analyse. Returns byte offsets and stays free of Langium services and the filesystem: cross-file targets come back as `{ kind: "module" | "file", ref }` for the consumer to resolve, then `findModuleTarget` locates the selected declaration inside the imported program
- `packages/core/src/keywords.ts` — single source of truth for the lexical surface (`RESERVED_KEYWORDS`, `BUILTIN_TYPE_NAMES`). Mirrored by hand from the Langium grammar; consumed by the playground's CodeMirror highlighter. Update both this file and the grammar together when adding a new keyword or type
- `packages/core/src/{expand,elaborate}.ts` — the module system (spec §9). `expandModule` (`expand.ts`) expands one module instantiation: substitute wired inputs, freshen private/output predicate names with a per-instance `$`-prefix, rename the selected output to the importer's name. Constructors are not renamed — they are qualified by their predicate (`opt::Some`), so renaming the head predicate carries them (`dist::Some`). `elaborate` (`elaborate.ts`) drives it recursively over a program's `:=` bindings — resolving imports via a `ModuleResolver` callback (so core stays filesystem-free), checking the instantiation graph is acyclic, selecting named or `?-` default outputs, and collecting data-file `DataSource`s plus `BoundaryConstraint`s. `checkModuleBoundaries` verifies the boundary column types against `publishedTypes` (the predicates' advertised contracts, not their inferred types) after `inferTypes`. `DatamogExecutor.prepareElaborated(source, resolve, file)` (engine) packages the whole pipeline (parseRaw → elaborate → postProcess → analyze → inferTypes → checkModuleBoundaries) with the resolver injected; the VS Code extension and the examples suite drive it, while the CLI runs the same stages inline (`loadProgram` in `main.ts`, then `analyze`/`inferTypes`/`checkModuleBoundaries`). Both resolve `from` imports from disk via `createNodeModuleResolver` (the `datamog-engine/module-resolver` subpath, Node/Bun only). The engine core stays filesystem-free, so the playground is unaffected
- `packages/engine/src/backend.ts` — `Backend` interface. SQL backends set `sqlDialect` and implement `execute`. Non-SQL backends set `sqlDialect: null` and implement the optional `evaluateProgram(analyzed, loaders)` (replaces the translate→SQL path) and `insertRows(decl, rows)` (replaces SQL INSERTs from loaders)
- `packages/engine/src/translator.ts` — AST → SQL generation; dialect-specific SQL controlled by `SqlDialect` interface. Per-rule body processing is two-pass: Pass 1 registers bindings from positive atoms; Pass 2 iterates to a fixed point over equalities and range atoms so forward references across the body are handled. Normalises runtime-partial operations to `NULL` across every backend: `/` and `%` wrap the divisor with `NULLIF`, `sqrt`/`ln`/`**` guard the argument with `CASE`. That NULL means "no value", and a definedness guard turns it into a withheld row: `canBeUndefined` (`core/src/partiality.ts`) decides where one is emitted, on head arguments, the sides of an equality, aggregates (via `HAVING`), and the parts of a `value` construction. Head and equality guards read the *unlifted* SQL, so a lift may not paper over an absence. The `**` operator (exponentiation, float-valued) and the bitwise operators go through a `bitwise` dialect hook. Synthesises an empty `WHERE 1 = 0` anchor for `WITH RECURSIVE` CTEs whose rules are all self-referential (least fixed point = empty)
- `packages/engine/src/dialect.ts` — `SqlDialect` interface (`supportsNonLinearRecursion`, view/CTE creation, range sources, aggregates, optional `divideIntegers` hook)
- `packages/engine/src/executor.ts` — `DatamogExecutor` class: orchestrates parse → analyze. If the backend implements `evaluateProgram`, delegates to it; otherwise runs the SQL pipeline (translate → createTables → load → createViews → check constraints → query)
- `packages/engine/src/result-coerce.ts` — cross-backend result uniformisation, applied to query rows (`executor.ts`) and constraint rows (`constraints.ts`) alike: `coerceBooleanColumns` (SQLite's 0/1 → `false`/`true`), `coerceNumericColumns` (Postgres `BIGINT`/`NUMERIC` arrive from `Bun.sql` as strings), `coerceJsonColumns` (SQLite's canonical TEXT → parsed JS). Each keys off the query's declared column types and is a no-op on backends that already return the right shape
- `packages/engine/src/constraints.ts` — `ConstraintViolationError`, violation formatting, and the row post-processing shared by the SQL and interpreter constraint checks. Both checks run before their query loop and throw with every violation collected
- `packages/backend/native/src/{base-evaluator,evaluator,planner,values,index}.ts` — naive bottom-up Datalog interpreter. `BaseDatalogEvaluator` (in `base-evaluator.ts`) holds EDB ingestion, query projection, dedup, and trace plumbing shared with the seminaive backend; `NaiveEvaluator` extends it and supplies only the naive fixed-point driver. `planner.ts` holds the shared planner/atom matcher/aggregate reducer/`enumerate` generator; `values.ts` reproduces the SQL translator's cross-backend invariants (null propagation, the absence marker, divide-by-zero, domain-error functions, slice bounds) directly in TS
- `packages/backend/seminaive/src/{evaluator,index}.ts` — seminaive variant. Extends `BaseDatalogEvaluator`; differs from naive only in the fixed-point driver: a priming pass (iteration 0) seeds via `all`, then each delta iteration fires every recursive rule once per stratum-body-atom position with that position reading from the previous iteration's delta. Terminates when every delta is empty.
- `packages/engine/src/loader.ts` — `ExtensionalLoader` plugin interface, `coerceValue`/`checkValue` for type validation. Loaders match external column/key names against declared columns by exact name (case-sensitively)
- `packages/engine/src/directory-loader.ts` — `createDirectoryLoader` factory shared by the csv/jsonl/json/mermaid loaders (file-per-predicate pattern). Bun-only (uses `node:path` + `Bun.file`) and exposed via the `datamog-engine/directory-loader` subpath so the browser playground bundle doesn't pull it in
- `packages/loader/json/src/json-loader.ts` — also exports `UrlJsonLoader` for HTTP/HTTPS JSON sources via the platform `fetch`. The whole-file parser lives in `parse-content.ts` (exposed via the `datamog-json/parse-content` subpath, mirroring csv/jsonl) so it can be bundled without dragging in the Bun-only `directory-loader`; `json-loader.ts` re-exports `parseJsonContent` for back-compat
- `packages/repl/src/{repl,boundary,events,index}.ts` — the session *driver*: it accumulates declarations/rules/queries and turns each chunk into events. The session itself is `IncrementalSession` in `packages/engine/src/incremental.ts`, injected as a `SessionFactory`. The CLI's `repl-driver.ts` wraps the driver for human use; `--repl --json` exposes a JSONL event stream for programmatic clients (datamog-magic)

## Datalog semantics

- **Extensional (EDB)**: declared with `input predicate`, data loaded via loader plugins. A column's `: type` is optional and defaults to `string` (cells load verbatim); annotate for a narrower type (e.g. `integer` for arithmetic, `value` for JSON). Using an unannotated column where `string` doesn't fit (e.g. `X * 2`) is a static type error
- **Intensional (IDB)**: defined by rules; the least fixed point of the union of all rules for the predicate
- Multiple rules for the same predicate union their tuple sets
- Linear recursion only — non-linear recursion is rejected at translation/evaluation time
- **Parity-stratified recursion**: a predicate name may carry a postfix `^` sigil (`bad^(E)`), marking it **maximal**: the anti-monotone side of a recursion through an even number of negations, which is what `forall` desugars to ("every child is constant"). Inside an SCC a positive call needs matching polarity and a negated call needs opposite polarity; with no sigil anywhere this degenerates to today's stratified negation. The sigil is written at every occurrence and is **not part of the name** (`bad` and `bad^` are one predicate; the analyzer checks every occurrence agrees), so module wiring and constructor qualifiers use the bare name while labels print the sigil. Such a stratum is evaluated by an **alternating fixed point** (`BaseDatalogEvaluator.runParityStratum`): minimal predicates rise from ∅, maximal ones start at ⊤ and are rebuilt from ∅ each round. ⊤ is never materialised — the polarity rule guarantees only negated atoms can observe it. Interpreter-only, like non-linear recursion. Which side carries the sigil is a modelling decision, not bookkeeping: both colourings type-check and give different answers (`examples/purity`). A sigil in a stratum with only one polarity is inert and warned about (`findInertPolarity`). See spec §4.3 and `doc/design/parity-stratification.md`
- **Aggregates**: aggregate functions (`count`, `sum`, `avg`, `min`, `max`, `concat`, `list`) in rule heads group by the non-aggregate head args; `count(*)` counts rows and `count(e)` counts every row where `e` has a value, a `null` included, so `count(X)` equals `count(*)` for any variable; `list` collects values into an array `value`, nulls included and sorting first (primitives are auto-lifted; sort key is the raw value for primitives, canonical text for `value` arguments); a row whose argument has no value contributes to no aggregate mentioning it and still counts for `count(*)`; aggregate predicates cannot be recursive; all rules for a predicate must agree on which positions are aggregates
- **Proof terms / ADTs**: naming a rule `p(...) :: Ctor` makes `p` a proof-carrying predicate (an algebraic datatype); it gains an implicit trailing `value` column holding the derivation as `{ "$proof": "p::Ctor", "args": [...] }`. Constructors are **scoped to their predicate** (`$proof` holds the qualified `pred::Ctor` name), so a tag is unique within a predicate but may recur across predicates. Bare `:: Ctor` auto-derives the args (existential witnesses then sub-proofs, don't-cares excluded); `:: Ctor(a, ...)` lists them explicitly. A constructor *term* is always a match (never a value builder), written bare `Ctor(...)` (resolved to the one predicate declaring the tag) or qualified `p::Ctor(...)` (required when several predicates share it); it desugars to a `scrut : Pred(_)` capture plus a qualified tag guard and per-arg accessors. **Match-only cuts both ways, and this is the thing to internalise before writing ADT code**: a constructor term in a rule *head* is also a match (`plus(Succ(A), B, Succ(C)) :- ...` range-restricts to proofs that already exist), so no rule can mint a node by naming a constructor. A nested constructor inside the head's args (`:: Nest(App(F, X), X)`) reads like construction but is a match too, and is the trap to watch for: it fires only when that inner node already exists, and otherwise derives nothing at all, silently and with no error. One node per derivation. **To build terms you derive new tuples of the proof-carrying predicate itself**, one of two ways: bound the universe with an index (`nat(n + 1) :: Succ :- nat(n), n <= 2` in `examples/peano`), or generate on demand with a request predicate plus a lookup rule (`sk() :: App(F, X) :- want(F, X).` alongside `app(F, X, T) :- T : sk, T = App(F, X).` in `examples/sk-proof-terms`, which needs several fixed-point rounds since an outer node cannot be requested until its inner nodes exist). A proof-carrying predicate's *body* atoms carry the implicit proof column too, so `p(V)` is an arity error where `V : p` is right. Output renders a proof bare (`Ctor(...)`), stripping the qualifier. Capture a proof with `V : p(...)`; `V : p` is shorthand for all-don't-care declared columns; `_ : p(...)` suppresses a sub-proof. The whole feature desugars onto the existing `value` machinery in `post-process.ts`, so the analyzer/translator/evaluators need no proof-term-specific code. See spec §8
- **Conditional expression**: `a if c else b`, postfix as in Python and right-associative, so it chains as an elif ladder. `if`/`else` are *contextual* keywords (they only ever follow a complete expression), so a predicate or variable may still be named `if`. The condition must be `boolean`; the result type is the join of the branches (`[1] if c else 2` is a `value`, the primitive branch taking the usual lift), and two branches with no join are an error rather than a widening. **Strict in the condition, lazy in the branches**: a null or absent condition withholds the row, matching `&&`/`!`/the orderings, and only the taken branch is evaluated (`7 if V > 0 else 0 / 0` is fine where `V > 0`). **Both branches must be non-nullable** (Position 3) while the condition need not be: a branch is what could make the *result* a null, and a conditional that could be both nullable and partial would need one SQL NULL to mean both. Emitted as `CASE c WHEN TRUE .. WHEN FALSE ..`, whose absent `ELSE` is what makes a NULL condition a NULL. See spec §2.6 and `doc/design/functional-sublanguage.md`
- **Optional head type annotations**: an intensional predicate's head terms may carry `: type` annotations (`ancestor(X: string, Y: string) :- ...`, including aggregate positions like `sum(Fee): float`). Checked, not used: inference runs unchanged and each declared type is verified against it. Per rule and per argument (a rule annotates any subset of its head arguments; sibling rules may annotate differently or omit), and a declared type must equal or widen the inferred one (annotate `value` to document looseness; a narrower claim than inference proves is rejected). No runtime effect. See spec §2.3 / §5.10
- **Head argument names**: a head term may be named with `as` (`p(count(*) as N, N + 1)`), which later positions in the same head can refer to. Head-scoped and substituted away by `substituteHeadNames` (`parser/src/head-names.ts`) at parse time, so nothing below the `:-` sees it. It is also the prerequisite for refining a computed position. See `doc/design/head-arguments.md`
- **Refinement annotations**: a `_` head position may carry a *proposition* over the head's other positions instead of a type (`span(X, Y, _: Y > X)`). The witness is erased, so the position is not a column; a refinement anywhere but a `_` is an error. A predicate's contract is the **disjunction over its rules**, so one unannotated sibling makes it vacuous, as does a refinement mentioning no head position (`_: 0 <= 0` is true of every tuple); `findInertContracts` (`core/src/contracts.ts`) warns about both, and `--strict-contracts` promotes them to errors. The whole feature lowers in `parser/src/refinements.ts` (`synthesiseContractChecks`, run first in `postProcess`) to one synthesised `!-` per contracted predicate, so no stage after parsing knows refinements exist. `core/src/obligations.ts` emits the per-rule obligations as SMT-LIB 2 under `--obligations`, and `cli/src/verify.ts` discharges them under `--verify` by spawning the solver `--solver` names (default `z3 -in`), one call per obligation so a malformed block cannot shift a verdict onto the wrong claim. No solver is a dependency; the test skips itself where none is installed. A rule may assume the contract of any predicate it calls positively, which at a self-reference is the induction hypothesis (sound because the induction is on the derivation and every rule of a predicate is discharged together or not at all). The encoder is QF_LIA, widening to QF_NIA on a nonlinear term; it confines every variable to the integer domain and drops the `$null` companion where nullness inference proves a variable non-null, without which every counterexample is an artifact. See spec §5.11 and `doc/design/refinement-annotations.md`
- **Integrity constraints**: a predicate whose extension must be empty; its tuples are the counterexamples. Two forms: anonymous `!- p(X), not q(X).` (a query-shaped conjunction, `'!' '-'` as two tokens so the lexer can't munch across the `!` operator; implicit projection names the witness columns) and named `error predicate orphan(X) :- ...` (a rule marker alongside `output predicate`). The analyzer routes both into `AnalyzedProgram.constraints` (kept apart from `queries` so positional result alignment holds and a constraint is never printed); the translator emits `translation.constraints` SELECTs. Checked after evaluation and **before any query runs**, so a violated program yields no results; all violations are reported, not just the first (`ConstraintViolationError` in `engine/src/constraints.ts`). No codegen difference from a query — only the disposition of a non-empty result. The REPL checks each constraint once, at its declaration (`IncrementalSession.appliedConstraints`). Module constraints survive elaboration and are checked per instance. See spec §2.10 / §4.7
- Don't-care variable `_` is desugared to unique anonymous variables in the parser
- **Modules**: an `input predicate` may be bound with `:=` to a data file (`:= "file" [as fmt]`) or an instance of another module (`:= [export] from "mod.dl"(moduleInput = pred, ...)`; omit the export for the module's `?-` default output). A file is a function from its inputs to its outputs; `elaborate` (in core) expands bindings into one flat program — resolving imports (via a `ModuleResolver` callback), freshening each instance (names contain `$`, unwritable by users), binding the importer's name to the selected output with a generated **alias rule**, checking the instantiation graph is acyclic, and type-checking the wiring boundaries. Instances are **shared**: identical (module file, input wiring) pairs expand once and get one alias per binding, so several outputs of one interface cost one copy of its rules. A **proof-carrying** selected output is renamed to the importer's name instead of aliased (so its constructors qualify as `local::Ctor`; an alias rule cannot carry a proof, since proof-carrying-ness does not propagate through a pass-through rule) and keeps its `output` marker so it still prints. It still shares: a second binding of the same instance and output adopts the first's predicate via `Context.nameAliases`, rewritten across the merged program at the end of `elaborate`, so equal wiring means one relation and one constructor, at the cost of the later declaration's column labels and its own line in `--all` (the shared relation prints once, under the first name). A receiving declaration for a proof-carrying output counts the implicit proof column, so it is one wider than the output's arguments. Every input of an *imported* module must be supplied (wired by an actual or `:=`-bound); an unsupplied one is a hard error (`elaborate` throws) — modules never auto-load. A `:=` binding on an input is an **overridable default**: an actual wired for it wins and the bound source is not instantiated, which is what lets a module read as an interface with default methods (inputs = required operations, `:=`-bound inputs = defaults, constraints = laws checked per instance). An actual naming a non-input is an error. Auto-loading a free input from `<name>.csv` is a CLI/playground convenience for the *entry* program only, not a language feature. See spec §9 and `doc/design/imports-as-functors.md`

## Runtime invariants (honoured by every backend)

The SQL translator and the native interpreter's `values.ts` both implement these so the same program produces the same result on every backend:

- **`null` is a value, undefinedness is partiality**: the two jobs SQL's one NULL used to share are separate. `null` is an ordinary value with its own type, storable in a `T?` column and spelled as JSON `null` inside a `value`. An operation with no result at its arguments has **no value**, which is not a value at all: no column holds it, no variable binds to it, and a conjunct mentioning one does not hold, so a rule whose head expression has no value derives no tuple. The interpreters carry both markers (`EvalResult = Value | undefined`); SQL has one NULL, so the *static* type decides which it means, and a `T?`-typed expression is never undefined. See `doc/design/null-as-a-value.md`, which supersedes `null.md`
- **Comparison**: no comparison operator ever returns `null`, but they split on what they do with one. There is one equality, `=`/`<>`, which is null-aware (`null = null` is true) and emits `IS NOT DISTINCT FROM` / `IS`, wrapped in a `CASE` with no `ELSE` when an operand can be undefined so the absence stays an absence; `!=` is a spelling of `<>` normalised away by `normalizeOperatorAliases` in `parseRaw`, and there is no `==`. The **orderings are strict** at a null and at an absence: `<`, `<=`, `>`, `>=` have no value there, emitted as the bare SQL operator. So is a **connective** past its dominating operand: `false && e` is `false` and `true || e` is `true`, but `null && true` and `!null` have no value. **Atom matching uses the same equality**, so a repeated variable joins NULL to NULL and `p(X), q(X)` means exactly `p(X), q(Y), X = Y`. A join takes the plain `=` where nullness inference proves either side non-null, which is what keeps a large join hash-joinable on Postgres; a genuinely nullable join still costs a quadratic plan there, which is accepted
- **`not` is not `!`**: `not e` is negation as failure over a body element and holds wherever `e` does not, absence included; `!e` is the boolean operator and propagates absence. They agree wherever the operand is defined. Nothing rewrites one into the other, and a negated filter carries its `negated` flag to the backends
- **An operation that computes requires a non-null operand**: arithmetic, negation, the bitwise operators, string concatenation, a subscript or slice index, a range bound, a builtin with a primitive parameter, and the aggregates `sum`/`avg`/`min`/`max`/`concat` reject a nullable one statically (`core/src/nullable-operands.ts`). Narrow with `X <> null` first; the comparisons and the connectives are exempt, and so is a `value` operand, which spells its null inside the value. This is what keeps a SQL NULL single-valued
- **Divide-by-zero / modulo-by-zero, domain-error math, integer overflow**: **no value**, so the row is withheld. `/`, `%`, `sqrt(-x)`, `ln(≤0)`, `-x ** fractional`, `0 ** -n`, `exp`/`**` overflow, a result outside `[-(2^53 - 1), 2^53 - 1]`, a non-finite float, a failed `to_*` / `as_*` / `parse_json`, and a missing `value` key are the list. SQL: the operation yields NULL and a definedness guard on the enclosing head argument or equality drops the row; interpreter: the absence marker. See spec §5.4
- **Bitwise / shift ops** (`& | ^ << >> >>>`): 32-bit signed two's-complement, Java/JS semantics (`>>` arithmetic, `>>>` logical, shift count mod 32). SQLite has no XOR/`>>>` and is 64-bit, so XOR is emulated and results are wrapped to int32; Postgres spells XOR `#` and emulates `>>>` via a bigint mask. See spec §5.9
- **Slice**: `W[i:j]` with `i >= j` returns `''` via an explicit guard (so SQLite doesn't walk backwards and Postgres doesn't error on a negative SUBSTR length)
- **Empty-group aggregates**: an aggregate folds a monoid, so over an empty group it returns that monoid's identity where the domain has one and has no value where it does not: `count` = 0, `sum` = 0, `concat` = `""`, `list` = `[]`, while `avg`, `min`, `max` and an overflowing integer `sum` withhold the tuple (via `HAVING` on the SQL backends). A rule with no grouping columns therefore derives one tuple where every head expression has a value and none otherwise, so mixing `count(*)` with `min(V)` derives nothing over empty input; one with a grouping column derives nothing. A head argument is a grouping column when it contains no aggregate *and* is not constant, where constant covers a literal, a negated numeric literal, and a variable the body binds to one. `isGroupingArg` in `core/src/analyzer.ts` is the single definition, called by the translator's `GROUP BY` and, via `hasGroupingColumns` beside it, by the interpreters' empty-group emission; three private copies drifted apart before it existed. See spec §2.7
- **Set semantics**: duplicate rows in EDB tables are deduplicated (SQL backends use `SELECT DISTINCT` against EDBs; interpreters dedup their tuple sets). IDB results are sets, not bags
- **Recursive-only predicates**: a predicate whose every rule is self-referential evaluates to the empty set. SQL: synthesised empty anchor (`SELECT CAST(NULL AS …) WHERE 1 = 0`) in `WITH RECURSIVE`. Interpreter: starts from `∅` and stays there

## Adding a new language feature

Typical touch points (in dependency order):

1. **Grammar** (`parser/src/datamog.langium`): add/modify rules; run `bunx langium generate` to regenerate `parser/src/generated/`
2. **Post-processing** (`parser/src/post-process.ts`): add transforms if the new feature needs AST normalization (name desugaring, type rewriting, …)
3. **Core re-exports** (`core/src/ast.ts`, `core/src/index.ts`): re-export new types from the generated AST; if the post-processed shape differs from the raw grammar shape (`AggregateCall`, `Subscript`/`Slice`), widen the relevant union here
4. **Analyzer** (`core/src/analyzer.ts`): update `checkSafety()` — phase 1 collects safe vars (fixed-point iteration over atoms + equalities + ranges), phase 2 walks body elements and reports unsafe variables with a source position
5. **Type inference** (`core/src/types.ts`): update var-type environment building in the fixed-point loop, add validation if needed. Column types must unify to a single basic type; `unifyColumnType` reports conflicts
6. **SQL translator** (`engine/src/translator.ts`): update `translateRule()` — Pass 1 registers bindings from positive atoms, Pass 2 iterates to a fixed point over equalities / range atoms; comparisons and non-binding equalities are collected and emitted as WHERE conditions at the end
7. **In-memory interpreters** (`backend/native/src/{planner,values}.ts`): mirror the new feature in the planner/value model so the native and seminaive backends produce the same results. `planner.ts` is shared with seminaive; `values.ts` is the place to land any new runtime invariant (NULL propagation, partial function, etc.)
8. **Lexical surface**, if the feature adds a keyword or operator: `core/src/keywords.ts` (feeds the playground highlighter and completion), `playground/src/lib/highlight.ts` (the CodeMirror stream tokenizer, which needs a hand-written branch for anything that is not a plain keyword), and `vscode-extension/syntaxes/datamog.tmLanguage.json` (hard-codes its keyword alternation, so it does not pick up `keywords.ts` automatically)

## SQL backends — compilation strategy and dialect differences

Each SQL backend implements `SqlDialect` (in `engine/src/dialect.ts`) and goes through `translator.ts`. Compilation maps:

- Non-recursive IDB → `CREATE [OR REPLACE] VIEW` (Postgres) / `CREATE VIEW IF NOT EXISTS` (SQLite/sql.js)
- Recursive IDB → `CREATE RECURSIVE VIEW` (Postgres) / `CREATE VIEW ... WITH RECURSIVE` (SQLite/sql.js). A predicate with **two or more recursive rules** cannot be a flat `anchor UNION rec1 UNION rec2` on Postgres, which permits one recursive term holding one reference to the CTE. The optional `SqlDialect.singleRecursiveTerm` hook folds them into one term naming the CTE once and unioning the rule bodies inside a `LATERAL`; `translateRule`'s `selfRef` parameter is what binds a rule's self-referencing atom to the outer alias instead of giving it a `FROM` entry. SQLite/sql.js accept the flat form, leave the hook undefined, and emit exactly what they did before
- Mutually recursive IDB → a combined CTE with a `__tag` discriminator on **every** SQL backend (neither engine can express an SCC as CTEs referring to each other; Postgres reports `mutual recursion between WITH items is not implemented`). The branch construction is shared as `mutualCteParts` in `engine/src/dialect.ts`; the dialects differ only in combining them (SQLite flat, Postgres folded through `singleRecursiveTerm` since the combined CTE has a branch per rule) and in padding narrower predicates (Postgres casts the NULLs, typing the CTE from its anchor). See `doc/design/postgres-alignment.md`
- Multiple rules for one predicate → `UNION`
- IDB views use positional column names (`col1`, `col2`, …); EDB tables keep their declared names

Dialect-specific quirks:

- **Range sources**: Postgres uses `generate_series`; SQLite/sql.js use recursive CTE subqueries (literal bounds inlined; correlated bounds capped at 1 000 000 since SQLite has no LATERAL)
- **`concat`**: `GROUP_CONCAT(expr, ',' ORDER BY expr)` (SQLite/sql.js) / `STRING_AGG(expr::TEXT, ',' ORDER BY expr)` (Postgres) — explicit `ORDER BY` so per-group output is deterministic
- **`list`**: `JSON_GROUP_ARRAY(json(valueSql) ORDER BY argSql)` (SQLite/sql.js) / `JSONB_AGG(valueSql ORDER BY orderKey)` (Postgres, with `orderKey = argSql::TEXT` for `value` args, `argSql` for primitives). The `FILTER (WHERE argSql IS NOT NULL)` is emitted only where the argument can be undefined, since then a NULL is an absence and contributes nothing; a nullable argument keeps its nulls, and a null sorts first. An empty group gives `[]`, `list`'s identity
- **Integer division**: Postgres and SQLite's `/` already truncates integers — no per-dialect override needed. The `divideIntegers` hook on `SqlDialect` is kept for future backends whose `/` is float-valued

## In-memory interpreters (native, seminaive)

Pure-TS backends that bypass SQL entirely; useful for the playground (no WASM bootstrap), for tracing/teaching, and as a reference implementation against which the SQL translators are checked. `BaseDatalogEvaluator` (in `packages/backend/native/src/base-evaluator.ts`) holds the parts shared with seminaive — EDB ingestion, planning, atom matching, aggregate reduction, query projection, dedup, trace plumbing. Subclasses differ only in the fixed-point driver:

- **Naive**: re-fires every rule each iteration until no new tuples appear
- **Seminaive**: a priming pass seeds via `all`, then each delta iteration fires every recursive rule once per stratum-body-atom position, with that position reading from the previous iteration's delta. Terminates when every delta is empty

`values.ts` reproduces the SQL translator's runtime invariants (null propagation, the absence marker, divide-by-zero, domain-error math, slice bounds) directly in TS — see the *Runtime invariants* section above.

## VS Code Extension

Langium-based language server providing syntax highlighting (TextMate grammar), semantic validation (runs analyzer + type inference), smart auto-complete, and go-to-definition. Completion and definition both **replace** their Langium defaults rather than extending them, because the grammar has no cross-references (`predicate=Identifier` is a plain string, not `[Predicate:IDENT]`) and both default providers work off resolved cross-references. `src/datamog-definition-provider.ts` delegates the lookup to core's `findDefinition` and adds only LSP range conversion plus disk reads for imported modules; it re-parses the buffer with `parseRawLenient` instead of reusing the Langium document, since the validator post-processes that AST **in place** (which is also why `completions.ts` filters `$anon` names). Built with `bun run build:vscode` → produces `datamog.vsix`. Also contributes a `datamog.run` command (`src/run-command.ts`) that evaluates the active buffer in-process via `DatamogExecutor` + the seminaive backend and prints its default output to a "Datamog" Output channel. It filters to the default the way the CLI does when given no output to select, since `analyzed.queries` holds one result per `output predicate` as well as one for the `?-` query, and the command has no flags to pick among them. Extensional data is loaded from sibling files next to a saved program by `src/disk-loader.ts` (a Node counterpart to the Bun-only directory loader: reads with `node:fs`, parses via the `datamog-{csv,json,jsonl}/parse-content` subpaths), one file per predicate (`<predicate>.csv`/`.json`/`.jsonl`). Both the run command and the validator resolve `:=` module imports from disk (via `DatamogExecutor.prepareElaborated` + `createNodeModuleResolver`, relative to the saved file); the validator re-parses a binding-using document into a throwaway AST so a `:=` binding is validated rather than flagged as an error.

## Conventions

- Parser uses Langium grammar (`datamog.langium`) with generated lexer/parser/AST; post-processing in `post-process.ts`
- Source positions available via Langium's `$cstNode` on AST nodes
- `ParseError` with line/column for user-facing error messages, `AnalyzerError` for semantic errors
- Tests use `bun:test` with TDD approach
- `Backend` is the abstraction for evaluation targets — implement it to add new databases (with `sqlDialect` + `execute`) or new non-SQL evaluators (with `evaluateProgram` + `insertRows`)
- Loaders use `coerceValue` (string → typed, for CSV/GSheet) or `checkValue` (native type validation, for JSONL)
- Example tests (`cli/test/examples.test.ts`) auto-generate `expected.json` if missing; delete it to regenerate. Examples no SQL backend can run (non-linear recursion, parity-stratified recursion) carry an empty `native-only` marker file in their dir: the sqlite run is skipped and seminaive becomes the canonical `expected.json` source
- The examples suite also runs every example on **sqljs**, whose one gap is recorded in `SQLJS_KNOWN_FAILURES`: sql.js's stock WASM build omits SQLite's math extension, so `LN` is missing, which takes out `ln`, `**` and `exp` (the last two guard against overflow with `LN(MAX_FLOAT)`). sql.js also defines `LOG` as the natural log where SQLite's extension makes it base 10; nothing emits `LOG`, so that one is latent
- The examples suite also runs every example on **postgres** when `DATABASE_URL` is set (skipped otherwise). That block shares one backend on a dedicated `new Bun.SQL(...)` connection (the global `Bun.sql` belongs to `backend/postgres/test`, and a closed connection cannot be reopened) and wipes the `public` schema between examples, since Postgres keeps tables and views across runs. - Examples run through `prepareElaborated`, so one may import modules with `:=` (see `examples/modular-order`). Keep the imported `.dl` files in the same directory; the entry point is then `<dir>.dl`, since a directory with several `.dl` files is otherwise ambiguous. The playground has no module resolver, so a module example cannot carry a `playground.json`
